# IR Tracking 操作手冊

技術背景見 [design.md](design.md)。這份只講怎麼跑。

## 前置

```bash
ssh carpi
cd ~/Car-and-Robotic-Arm && git pull
```

先用 `git status --short` 檢查 Pi；`scratch/` 和未追蹤 LOG 可以保留，但不要在有已追蹤
檔案修改時直接 pull。

## Phase 1：感測器檢查（~2 分鐘，不動馬達，SSH 安全）

```bash
scripts/map1-phase1-ir-check.sh
```

把車放在軌道旁，手動移動感測器，確認：

| 條件 | 板載 LED | 正規化讀數 |
|---|---|---|
| 白紙 | 全暗 | `0 0 0 0` |
| 黑線（中間兩顆壓線） | 中間兩顆亮 | 中間兩顆 = 1 |
| 整台拿起來離地 | **全亮** | `1 1 1 1` |

**離地讀起來跟黑線一樣是正常的** —— 兩者都是弱回波。這也是為什麼紙面起伏會造成
「假黑」而不是「假白」。

讀數對不上就**不要往下做**，先看 §疑難排解。

## Phase 2：馬達低速測試（~3 分鐘）

🔴 **先把四個輪子抬離地面或用卡具固定底盤。**

```bash
PYTHONPATH=src python3 examples/37_map1_motor_test.py
```

確認四顆馬達轉向正確、沒有異音。

---

## Phase 3：乾跑（~2 分鐘，不動馬達）

車放在起點線上，**不接馬達電**：

```bash
PYTHONPATH=src python3 examples/39_map1_ir_line_follow.py --dry-run --duration 60
```

手動推著車沿線走，看每一幀的輸出。要確認的是：

- 位元字串是 **`P1 P2 P3 P4` 實體順序**，車往右偏時 `P3`/`P4` 那側要先亮
- 車正在線上時應該大量出現 `P0110`，`kind` 顯示 `on_line`
- 結束摘要的 **Noise/hold frames 要低於 5%**

> **超過 5% 就不要實跑。** 那代表感測器讀到單一條線做不出來的組合 —— 通常是
> 離地高度不對或某顆電位器飄掉，先修好再說。

## 驗證階段 4：逐一測試 Map Phase（操作者站在車旁）

🔴 **操作者必須站在車旁，隨時能切斷主電源。**

不要從完整一圈開始。`40_map1_ir_phase_test.py` 使用和 Example 39 相同的正式控制路徑，
但一次只允許一個有距離上限的 Map Phase。Phase 2–10 執行前，依終端印出的 entry pose
把車手動放到該段起點。

```bash
# 發車盲走 + 右轉，預設 20 秒證據窗口。
# 直行預設 PWM 150 / 2.2s；右轉同樣用 PWM 150，90° 目標加 5° 補償，約 2.80s。
PYTHONPATH=src python3 -u examples/40_map1_ir_phase_test.py --phase 1

# 車放在 Phase 2 起點、車頭朝東，只測東向 15.5cm 循線
PYTHONPATH=src python3 -u examples/40_map1_ir_phase_test.py --phase 2

# Phase 3 可放在 Phase 2 任意穩定 P0110 處、車頭朝東；程式自行偵測 ARC 1
PYTHONPATH=src python3 -u examples/40_map1_ir_phase_test.py --phase 3
```

Phase 1 的直行與右轉 PWM 已分開：`--phase1-forward-speed` 只改直線扭力，`--speed`
控制右轉與後續循線。2026-08-21 的 PWM 150 / 4.0s 實跑只在第一秒前進，之後三秒輪子
停止但馬達持續嗡鳴。LOG 證明 P0000 後命令仍持續；操作者之後找到真正原因是底盤被
翹起的紙卡住。先前約 7cm 的結果不是速度校正，3.66 秒值已作廢。把紙弄平後重新測試
1.6 秒仍不足 16cm，因此只把直行試調為 PWM 150 / 2.2 秒。之後右轉實測仍不足 90°，
所以保留 90° 路徑目標並增加 5° 開迴路脈衝補償；右轉時間約由 2.68 秒增至 2.80 秒。
定時馬達命令現在每 0.01 秒重送一次，與已能持續行駛的 100Hz 正式導航迴圈一致；LOG
每 0.1 秒留下命令與當下 IR 快照，標記成 `OBSERVE ONLY`。IR 只用於事後對時，絕不
參與 Phase 1 控制。

如需單獨微調直行，只改一個參數並記錄實際距離，例如：

```bash
PYTHONPATH=src python3 -u examples/40_map1_ir_phase_test.py --phase 1 \
  --phase1-forward-speed 150 --phase1-forward-s 2.2
```

每一段都必須記錄實際距離、結束方向、SEARCH/REVERSE 次數與 LOG 路徑。前一段未通過，
不要測下一段。

Phase 2 獨立測試會先執行主動 acquisition：看到偏左／偏右黑線時原地朝該側修正，經過
相鄰的 `P0000` 時保持同方向，直到 `P0110` 穩定 0.10 秒才開始計算 15.5cm。若在
`--start-acquire-timeout-s` 內無法置中，程式會停輪並退出。Phase 3、5、7、9 獨立測試
不再把 `--speed` 暗中乘以 0.6；`--speed 150` 的外側／基準輪現在確實使用 PWM 150，
避免 PWM 90 只讓馬達嗡鳴。ARC／圓環上的 `P0111`、`P0011`、`P1110`、`P1100` 可能是
緊曲線同時覆蓋相鄰感測器，不是要執行的路口；只有獨立曲線測試會使用其左右偏移轉向。
直線 Phase 與完整路線仍必須由有序路口訊號確認，不能用單一 junction-shaped reading
擅自轉向。

2026-08-21 06:15 的 ARC 1 實跑在軟體估算 12cm 時只走到實體曲線約一半；LOG 顯示停止
發生在 `STOP-AFTER-PHASE 3`，不是 `P1000` 讓馬達停止。第一次先把距離信用調成 50%，
但 06:46 已能正常左轉的實跑仍只由 east 轉到 northeast，因而一度把信用再降至 25%。
06:51 的 25% 實跑證明這個推論錯誤：程式在每次 `P0110` 時都回到 `L150/R150` 沿切線
直走，4.5 秒起持續 `P1111`，車子已離開有效路徑，延長時間只讓錯誤持續更久。

07:03 的測試確認實際放置方式不是 ARC 1 接口，而是 Phase 2 東向直線任意 `P0110` 點。
舊程式卻從第一幀就啟用左彎，因而離開直線、倒退回線、再左彎，12 秒內重複 recovery
六次。Phase 3 現在先用普通 Phase 2 循線，只有看到實測入口序列
`P0100 -> P0000 -> P1000` 或左側曲線形狀 `P1100/P1110`，才切換 LEFT ONLY。

Phase 3 不再使用 12cm PWM／時間估算停止。車上沒有 wheel encoder，這個估算已多次在
ARC 尚未走完時提前停車；LOG 會顯示 `pc=disabled`。操作者在車頭朝北時可按 `Ctrl+C`，
否則由 `--duration 20` 作為唯一自動安全上限。Phase 5/7 的距離門檻尚未因此自動取消，
必須等各自實測後再決定。
Phase 3 必須在線上以 north heading 停下，才能開始 Phase 4。

2026-08-21 06:21 的下一次 ARC 1 實跑確實走得更長，但仍衝出路徑。現場確認車身右側的
`P0010`、`P0001`、`P0011`、`P0111` 是地圖紙張凸起造成的假黑，不是 ARC 1 向右彎。
Phase 3 從東轉向北，只允許直行或左修正：上述右側訊號現在會標記為
`opposite-side noise ignored`，保持最近一次安全的直行／左轉命令，也不會污染
`_last_localising`。若讀到 `P0000`，搜尋只會原地向左；到達搜尋角度上限仍看不到有效
黑線就停車，不會出現向右回掃。

ARC 1（east → north）、ARC 2（north → west）、ARC 3（west → southwest）在地圖上都是
左彎，因此相同限制現在由 phase 規格統一套用到獨立 Phase 3、5、7。三段都只允許直行
或左修正，右側訊號視為凸紙噪音；直線段與 Phase 9 圓環仍維持原本的雙向循線。ARC 2、
ARC 3 尚需各自實跑確認，不能只因共用邏輯就視為已通過。

06:39 的 Phase 3 LOG 證明右轉已完全消失，但原本的「忽略」仍會保持最近命令；如果最近
剛好是置中 `L150/R150`，車子就會在左彎上繼續直走。現在右側噪音會沿用最近一次有效
左修正，即使中間曾短暫回到 `P0110` 也不清除；若從起點到噪音出現前都沒有左修正歷史，
則使用溫和左修正 `L110/R150`。因此噪音期間不再直行，也不會右轉。

地圖外的地毯會讀成 `P1111`。06:51 的 LOG 顯示舊程式先在地毯上前進 2 秒才倒退，又只
倒放最近 2 秒，所以最多回到紙張邊緣；接著右側 `P0111` 噪音還會過早結束倒退。獨立
ARC 3/5/7 現在持續 `P1111/P0000` 0.3 秒就開始 recovery，保留 3 秒命令歷史，且倒退時
忽略右側與不連續 NOISE，直到真正看到 `P0110` 或左側有效黑線才恢復前進。完整路線仍
保留原本 2 秒 dwell／2 秒 history，避免在真正路口上過早倒退。

07:00 的 Phase 3 測試全程保持左彎且沒有離線，但 x0.50 距離係數在 4.3 秒提前結束，
車頭只到東北而非朝北。獨立 ARC 3/5/7 現改用 x0.25，預期在相近命令下約 8.6 秒才到
12cm 邊界。只有車頭朝北且感測器仍壓在線上，才算 Phase 3 通過。

## 驗證階段 5：整合實跑

只有 Phase 1–10 個別通過後才執行。Phase 1 右轉後會**保持停車**確認穩定 ON_LINE/DRIFT；
找不到 Phase 2 黑線會安全結束，不再盲目前進最多 3 秒。

先跑這個 —— 車放在**東西向的線上、車頭朝東**，跳過發車區支線：

```bash
PYTHONPATH=src python3 -u examples/39_map1_ir_line_follow.py --duration 120 --start-on-loop --laps 1
```

先驗迴圈邏輯，不讓一次性的支線 T 路口攪進來。log 每行第三欄會印**下一個預期路口**，
摘要會印被距離閘門擋掉的次數。一圈的順序應該是：

```
roundabout entry (右轉) → roundabout exit (右轉) → T junction (直行) → 回到 entry
```

通過之後才換成從發車區起跑（車頭朝北）：

```bash
PYTHONPATH=src python3 -u examples/39_map1_ir_line_follow.py --duration 120 --laps 1
```

`-u` 不能省 —— 沒有它 stdout 會被 block buffer 住，程式跑完才吐 log，中途看不到任何東西。

隨時 `Ctrl+C` 停止。如果收尾印出 `WHEELS MAY STILL BE TURNING`，**立刻切電源**：
那代表停車指令沒能送到板子。

## 調參

一次只改一個，改完重跑。

| 症狀 | 調哪個 |
|---|---|
| 直線上蛇行 | 內輪速調高（110 → 125） |
| 偏了才修、來不及 | 內輪速調低（110 → 95） |
| 路口沒轉就開過去 | `--junction-min-s` 調低 |
| 直線上誤判成路口 | `--junction-min-s` 調高 |
| 轉彎前就開始轉 | `--creep-before-turn-cm` 調高 |
| 轉彎轉過頭才轉 | `--creep-before-turn-cm` 調低 |
| 圓環切出去 | 圓環內降速（尚未實作，見 README 待決事項） |
| Noise 幀數高 | **墊高感測器到約 2 cm**，或重調電位器 |

## 疑難排解

**四路讀數同時亂掉、前後矛盾** → **不是感測器壞掉**，是供電或接線。先檢查
`VCC`（Pin 1）和 `GND`（Pin 14）的杜邦線，再確認 Pi 沒有在重開機。真正故障的通道
會自己卡住，不會拖著另外三路一起亂。

**某一路持續讀黑、其他三路正常** → 那一顆的電位器轉到工作範圍邊緣了，或那一顆
離地距離跟其他三顆不同（感測條沒平貼）。

**極性整組相反** → 電位器重調後極性可能翻轉。用 Phase 1 的三個條件重驗，必要時
改 `--invert`。**極性不能只看單張快照判斷** —— 要用連續記錄、在記錄過程中改變條件。

**車一直進 SEARCH** → 先看 `0000` 前面那一幀是什麼。如果前面是 `0010`/`0100`，
那是盲區被誤判成丟線；如果前面是 `0001`/`1000`，那是真的丟了。
